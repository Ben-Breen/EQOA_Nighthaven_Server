# Protocol and client unknowns inventory

This inventory describes the evidence currently present in Nighthaven's documents. It is not a protocol specification. The historical implementation is evidence about that implementation only.

## Evidence labels and methods

Use the evidence vocabulary from [architecture.md](architecture.md): `CONFIRMED — reference`, `CONFIRMED — client/protocol`, `INFERRED`, `UNKNOWN`, `HISTORICAL CHOICE`, `NIGHTHAVEN DECISION`, and `REJECTED LEGACY BEHAVIOR`.

Method tags used below:

- **S — Static archaeology:** source, serializers, schemas, comments, config and external documentation. Establishes what a codebase says or does, not what the target client requires.
- **C — Original-client observation:** passive packet capture or controlled experiment with an original PS2 client and exact revision documented.
- **E — Emulator/runtime instrumentation:** PCSX2 or other optional client runtime observation. Useful for rapid experiments; does not establish identical original-hardware behavior.
- **D — Differential:** compare client capture/behavior with reference implementation behavior or a controlled configuration change. Helps separate client expectation from a particular server's choices.

No `CONFIRMED — client/protocol` evidence exists in the current Nighthaven documents. Existing opcode and parser notes are `CONFIRMED — reference` only.

## Static-versus-runtime resolution summary

- **Static archaeology can establish:** what the public server parses, serializes, configures and persists; declared opcode values; CRC implementation; state transitions coded; and external project documentation claims. It can disprove statements about absent handlers in the surveyed version but cannot prove client requirements.
- **Original-client observation is required for:** actual bootstrap destinations, packet ordering, target endpoints, field behavior, state transitions, retries, timing, client acceptance/rejection, and hardware-specific behavior.
- **Emulator/runtime instrumentation can isolate:** rapid packet capture and repeatable one-variable experiments, DNAS gate timing, endpoint choices and basic client reactions. Every result must be labeled emulator-specific until confirmed on original PS2 hardware where practical.
- **Differential evidence should compare:** captured client behavior, reference server behavior, and controlled changes (one at a time). A reference server response is not a client requirement unless the client behavior independently demonstrates it.
